# Лабораторная работа № 6. Построение CI-конвейера для C++-проекта DataConverter

## 1. Что сделано локально

Чужой проект из папки работы удалён. На его место положен DataConverter.

Локальная проверка на macOS (AppleClang 17, CMake):

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

Результат: 13 тестов из 13 прошли. Утилита переводит `examples/people.csv` в JSON и `examples/people.json` в YAML.

Конвейер описан в `.github/workflows/ci.yml`. Сами прогоны GitHub Actions, скриншоты и замеры времени выполняются после создания репозитория. Ниже указано, что именно смотреть и какие выводы из этого следуют.

## 2. Структура проекта и команды

| Что | Зачем |
| --- | --- |
| `src/converter.cpp`, `src/converter.hpp` | преобразование CSV, JSON и YAML |
| `src/main.cpp` | CLI: `dataconv <вход> <выход>` |
| `tests/converter_tests.cpp` | 13 модульных тестов |
| `third_party/nlohmann/json.hpp` | JSON, только заголовок |
| yaml-cpp 0.9.0 | YAML, скачивается CMake FetchContent |
| GoogleTest 1.14.0 | тесты, скачивается CMake FetchContent |
| `examples/` | примеры данных, в сборку не входят |

Команды, которые повторяет CI:

1. `cmake -S . -B build -DCMAKE_BUILD_TYPE=Release` — конфигурация и загрузка зависимостей в `build/_deps`.
2. `cmake --build build --config Release --parallel` — сборка.
3. `ctest --test-dir build --output-on-failure` — тесты. На Windows добавляется `-C Release`, потому что Visual Studio собирает конфигурации в разные каталоги.

Если конфигурация, сборка или тесты завершаются с ненулевым кодом, шаг GitHub Actions падает, и задание считается неуспешным. Отдельный `continue-on-error` не включён.

## 3. Конвейер

Файл `.github/workflows/ci.yml`.

- События: `push`, `pull_request`, плюс ручной запуск `workflow_dispatch`.
- Одно задание `build-and-test` разворачивается матрицей в три: `ubuntu-latest`, `macos-latest`, `windows-latest`.
- `runs-on: ${{ matrix.os }}` — у каждой ОС свой чистый runner.
- Шаги: получить код (`actions/checkout`), поставить инструменты сборки, восстановить кэш `build/_deps`, сконфигурировать CMake, собрать, запустить тесты, выгрузить артефакты.
- На Ubuntu ставятся `build-essential` и `cmake`. На macOS уже есть Clang и CMake, на Windows — MSVC и CMake. yaml-cpp и GoogleTest на всех системах ставит сам CMake.
- Стандарт C++17, исходники и набор тестов общие: матрица не подменяет код, она меняет только ОС.

### Почему сборка на Ubuntu не гарантирует сборку на Windows и macOS

Одинаковый C++17 и одни и те же тесты всё равно исполняются разными компиляторами и генераторами CMake.

- Ubuntu: GCC и Unix Makefiles, результат в `build/dataconv`.
- macOS: Apple Clang.
- Windows: MSVC и генератор Visual Studio. Это многоконфигурационная сборка, программа лежит в `build/Release/dataconv.exe`, а `ctest` нужно вызывать с `-C Release`.
- Различаются стандартные библиотеки, пути, разделители, чувствительность файловой системы к регистру, оболочки и перевод строки.
- Ошибка может проявиться только у одного компилятора. В этом проекте yaml-cpp специально взят версии 0.9.0: в 0.8.0 не хватало `#include <cstdint>` для GCC 15, тогда как другой компилятор мог собрать старую версию без этой ошибки.

Успех на одной машине проверяет только её компилятор, заголовки и генератор CMake.

## 4. Параметр fail-fast

В репозитории оставлено `fail-fast: false`, тесты рабочие. Так одно падение не скрывает результат на других ОС.

Эксперимент делается уже на GitHub, двумя push подряд. Контролируемая ошибка — в `tests/converter_tests.cpp`, тест `Converter.CsvToJson`:

```cpp
EXPECT_EQ(result[0]["name"], "Eva");
```

заменить ожидаемое значение на `"Broken"`. Этот тест есть на всех трёх ОС, поэтому сломается каждая система, а не одна.

**Прогон A, `fail-fast: false`.** Закоммитить сломанный тест и запушить. Все три задания дойдут до тестов и завершатся ошибкой. GitHub никого не отменит: в списке будут три красных задания со статусом Failure. В журнале CTest упадёт `Converter.CsvToJson`.

**Прогон B, `fail-fast: true`.** В `ci.yml` поставить `fail-fast: true`, сломанный тест не чинить, запушить снова. Как только одно задание матрицы падает, GitHub отменяет ещё не законченные задания этой матрицы. У них статус Cancelled, а не отдельный результат тестов. Задания стартуют параллельно, поэтому часто успевают упасть два, а третье отменяется. Реже все три успевают упасть сами, если тесты завершились раньше сигнала отмены. Разница с прогоном A в том, что отмена вообще включается только при `true`.

**После эксперимента.** Вернуть `"Eva"`, вернуть `fail-fast: false`, запушить. Должны быть зелёными все три ОС. В отчёт вставить скриншоты A, B и финального зелёного прогона.

`fail-fast: true` экономит минуты, когда ошибка общая и остальные ОС уже ничего не добавят. `fail-fast: false` нужен, когда важно увидеть, не сломана ли только одна платформа: отмена спрятала бы этот ответ.

## 5. Кэширование

Кэшируется каталог `build/_deps`: исходники и результаты сборки yaml-cpp и GoogleTest. Свой код проекта маленький, основное время первого прогона уходит на скачивание и компиляцию этих библиотек.

Ключ:

```text
${{ runner.os }}-deps-${{ hashFiles('CMakeLists.txt', 'src/**', 'tests/**', 'third_party/**') }}
```

- `runner.os` разделяет кэш Ubuntu, macOS и Windows. Объектные файлы и пути из `build/_deps` с одной системы нельзя подставить в другую.
- `hashFiles(...)` меняет ключ, если меняются файл сборки, исходники или заголовок JSON: от них зависит, можно ли безопасно переиспользовать сохранённое дерево.
- `restore-keys: ${{ runner.os }}-deps-` позволяет взять последний кэш той же ОС, если точный ключ не совпал.

Что записать из вкладки Actions (длительность задания и текст шага Cache):

| Прогон | Ubuntu | macOS | Windows | Что написано на шаге Cache |
| --- | --- | --- | --- | --- |
| 1. Первый push | | | | Cache not found |
| 2. Re-run all jobs без изменений кода | | | | Cache hit |
| 3. Изменён один исходный файл, новый push | | | | точного ключа нет, взят restore key |

Прогон 2: Actions → удачный workflow → Re-run all jobs. Код тот же, ключ тот же, зависимости не качаются и не пересобираются с нуля.

Прогон 3: достаточно комментария в `src/converter.cpp`. Хеш исходников другой, точный ключ не находится. Префикс `ubuntu-deps-` / `macOS-deps-` / `Windows-deps-` всё ещё подходит, поэтому GitHub отдаёт предыдущий каталог зависимостей. Полной холодной сборки снова нет, но это уже не exact hit: в логе будет restore key, и после прогона сохранится новый кэш.

Кэш полезен, когда повторный прогон может переиспользовать уже скачанные и собранные зависимости. Он не ускоряет каждый запуск:

- первый прогон кэш только заполняет;
- при смене ключа и отсутствии подходящего restore key работа начинается заново;
- неиспользуемый кэш GitHub удаляет (порядка 7 дней), есть и ограничение объёма репозитория;
- восстановление большого архива само занимает время;
- изменённый `.cpp` всё равно компилируется: кэш зависимостей этого не отменяет;
- смена образа runner может сделать старый `build/_deps` непригодным, и конфигурация начнётся заново.

## 6. Артефакты

После тестов каждое задание выкладывает:

- `test-report-<ос>` — каталог с `junit.xml` и `ctest.log`. Отчёт выгружается и при падении тестов (`if: always()`).
- `dataconv-<ос>` — собранная программа, только если сборка и тесты прошли.

Где смотреть: открытый прогон workflow, блок Artifacts внизу страницы. Скачать нужно хотя бы один `test-report-*`, распаковать zip и открыть `junit.xml`. Внутри набор тестов `Converter.*`, их 13, ошибки отсутствуют. В `ctest.log` те же тесты со статусом Passed.

Кэш и артефакты решают разные задачи.

| | Кэш | Артефакт |
| --- | --- | --- |
| Задача | ускорить следующий прогон | сохранить результат этого прогона |
| Кто читает | следующий job той же ОС | человек через интерфейс Actions |
| Пример | `build/_deps` | `junit.xml`, программа `dataconv` |
| Срок | пока ключ жив и кэш не вытеснен | привязан к конкретному запуску workflow |
| Гарантия | может не подойти или отсутствовать | остаётся у этого прогона, пока его не удалят |

Кэш нельзя считать результатом лабораторной: его может не быть на следующем запуске. Артефакт как раз для того, чтобы отчёт о тестах можно было скачать и проверить.

## 7. Контрольные вопросы

**Что такое непрерывная интеграция и какую проблему она решает?**  
Это регулярная автоматическая сборка и проверка проекта при изменениях. Она ловит поломку сразу после коммита, а не перед сдачей, и делает проверку одинаковой для каждого изменения.

**Что такое workflow в GitHub Actions?**  
Это описанный в `.github/workflows/*.yml` процесс: по каким событиям запускаться, какие задания выполнить и на каких машинах. В этой работе workflow называется DataConverter CI.

**Чем отличаются события push и pull_request?**  
`push` запускает конвейер, когда коммиты попадают в ветку репозитория. `pull_request` запускает его для предлагаемых изменений из запроса на слияние, ещё до попадания в основную ветку. Так проверяется и прямая запись в репозиторий, и чужой вклад.

**Что такое job и step?**  
Job — группа шагов на одном runner, со своим `runs-on`. Step — один шаг внутри job: команда оболочки или action вроде `checkout`. Шаги одного job видят общие файлы. Разные job друг друга не видят, пока файлы явно не передали кэшем или артефактом.

**Для чего используется runs-on?**  
Он выбирает виртуальную машину, на которой выполнится job. Здесь это значение из матрицы: Ubuntu, macOS или Windows.

**Как работает strategy.matrix?**  
Одно описание job умножается на набор значений. `os: [ubuntu-latest, macos-latest, windows-latest]` даёт три независимых задания. В шагах `${{ matrix.os }}` подставляется ОС этого задания.

**Почему задания матрицы выполняются в отдельных средах?**  
Каждое задание матрицы — отдельный job со своим runner. Общего диска нет, компилятор и пути одной ОС не влияют на другую. Иначе проверка трёх систем была бы недостоверной.

**Для чего предназначен параметр fail-fast?**  
Он решает, останавливать ли остальные задания матрицы после первой ошибки. `true` отменяет ещё идущие задания. `false` даёт каждой ОС дойти до своего результата.

**Чем кэширование отличается от сохранения артефактов?**  
Кэш хранит промежуточные данные для ускорения будущих сборок. Артефакт хранит результат конкретного запуска, чтобы его можно было скачать. Кэш может пропасть или не подойти по ключу. Артефакт остаётся результатом этого прогона.

**Почему кэш следует разделять по операционным системам?**  
В `build/_deps` лежат уже собранные yaml-cpp и GoogleTest, пути и формат объектных файлов. Библиотека, собранная GCC на Ubuntu, не является библиотекой для MSVC или Apple Clang. Общий ключ без `runner.os` подставил бы чужие файлы и сломал бы сборку. В ключе это учтено через `${{ runner.os }}`.

**Почему проект может собираться на Ubuntu, но не собираться на Windows или macOS?**  
Потому что компилятор, генератор CMake, расположение результата, системные заголовки и правила оболочки другие. Ошибка в коде, переносимом только на GCC, или шаг CI, написанный только под bash-пути Linux, на Windows не повторят успех Ubuntu. Поэтому в конвейере для Windows отдельно указан `ctest -C Release`.

**Какие преимущества даёт автоматический запуск тестов при каждом изменении репозитория?**  
Тесты не забывают запустить. Одинаковые 13 тестов идут на трёх ОС при каждом push и pull request. Ошибка видна в том коммите, который её внёс, а отчёт сохраняется артефактом. Перед слиянием запроса видно, проходит ли проверка, без ручной сборки на каждой системе.

## 8. Что заполнить после прогонов на GitHub

1. Времена трёх прогонов из раздела 5 и фразы Cache hit / restore key.
2. Скриншот зелёной матрицы из трёх ОС.
3. Скриншоты fail-fast `false` (три Failure) и `true` (есть Cancelled).
4. Скриншот блока Artifacts и пара строк из скачанного `junit.xml`, где видно число тестов.
